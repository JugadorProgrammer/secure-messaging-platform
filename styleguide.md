# Руководство по стилю

Правила исходного кода FRONT.

Стек: Next.js (App Router), React, TypeScript, shadcn/ui, CSS-модули по БЭМ, Zustand.

Исходные файлы кодируются в UTF-8.

## Архитектура

Приложение разделено на четыре слоя.

### Слои

| Слой           | Каталог                       | Состав                                                   |
|----------------|-------------------------------|----------------------------------------------------------|
| Представление  | `src/app`, `src/presentation` | маршруты, компоненты, стили, состояние интерфейса        |
| Приложение     | `src/application`             | сервисы приложения                                       |
| Бизнес-логика  | `src/domain`                  | сущности, объекты-значения, доменные сервисы             |
| Инфраструктура | `src/infrastructure`          | вызовы внешних сервисов, их DTO                          |

Интерфейсы именуются с `I`, и используются как для различных архитектурных решений, так и для декларации зависимости на вышестоящие слои.

Пример дерева для рабочего стола и расшифрования сообщения.

### Роль архитектурных слоёв

Слой бизнес-логики хранит сущности, объекты-значения и доменные сервисы. Зависимостей на другие слои нет. Если нужна операция другого слоя, доменный сервис задаёт интерфейс, и его реализуют снаружи.

Слой приложения координирует действия над бизнес-логикой и ходит во внешние сервисы через интерфейсы. Реализация интерфейса лежит в слое приложения или в инфраструктуре. Сервис необходимо реализовывать по принципу единой ответственности - он не должен уметь много, но тесные сценарии между собой объединяют в одном сервисе
или выносят общую часть в сервис, который с которым связываются через композицию.

Слой представления — маршруты, компоненты и состояние интерфейса. `page.tsx` не имеет разметки экрана, вызывает сервис из `appconfig.ts` и отдаёт результат компоненту. Клиентский компонент вызывает функцию из `src/presentation/api`. `layout.tsx` — оболочка группы маршрутов. `loading.tsx` и `error.tsx` — у маршрута с ожиданием и ошибкой.

Инфраструктурный слой отвечает за интеграции, реализации интерфейсов нижних слоёв и обмен сообщениями.

### appconfig.ts

`src/appconfig.ts` — конфигурация приложения. Зависимости подаются через DI.

Модуль серверный (`import 'server-only'`). Его импортируют `page.tsx`, `layout.tsx`, Server Action и Route Handler.

### HTTP API

Route Handler лежит в `src/app/api/<ресурс>/<действие>/route.ts` и экспортирует `GET`, `POST`, `PUT` или `DELETE`. Handler вызывает сервис из `@/appconfig`. Серверный компонент вызывает сервис напрямую.

Клиентская функция лежит в `src/presentation/api/<ресурс>.ts`. Ответ `fetch` имеет тип `unknown`. Для приведения к контракту данных нужен middleware.

Server Action вызывает сервис из `@/appconfig` и своего URL не имеет.

### Порядок в файле

Порядок частей файла:

1. импорты;
2. типы;
3. экспортируемая реализация;
4. вспомогательные функции этого файла.

Между присутствующими частями одна пустая строка.

Внутри компонента порядок такой: состояние, вычисления, обработчики, разметка.

## TypeScript

Включён `strict`.

Тип указывается у пропсов, у аргументов экспортируемой функции и у состояния хранилища. Тип локальной переменной
указывается, когда вывод неочевиден.

`any` не используется. Значение неизвестной формы имеет тип `unknown` и сужается проверкой.

Non-null assertion `!` не используется.

Type assertion `as` допустимо в инфраструктурном слое на границе с внешними данными и стоит рядом с проверкой их формы.

Пропсы описываются через `type` с именем `{Компонент}Props`. Объединения и результаты сервисов описываются через `type`.

Пример пропсов.

```ts
type MessageListProps = {
    dialogId: string
    isEmpty: boolean
}
```

Компонент объявляется именованной функцией. `React.FC` не используется.

`page.tsx`, `layout.tsx`, `loading.tsx` и `error.tsx` экспортируют компонент по умолчанию. `route.ts` экспортирует
функции HTTP-методов по имени. Остальной код экспортируется по имени.

Пример компонента.

```tsx
export function MessageList({dialogId, isEmpty}: MessageListProps) {
    return <section>{dialogId}</section>
}
```

## Компоненты

Компонент по умолчанию серверный.

`'use client'` ставится на компонент, которому нужны состояние, обработчик события, браузерное API или хранилище
Zustand. Такой фрагмент выносится в отдельный клиентский компонент. Маршрут из-за этого клиентским не помечается.

Имя события в пропсах начинается с `on`. Имя обработчика начинается с `handle`. Имя булева пропа начинается с `is`.

Пример: `onSelect`, `handleSelect`, `isEmpty`, `isUnread`.

Переход внутри приложения выполняется через `next/link`. Изображение выводится через `next/image` с заполненным `alt`.
Действие без смены маршрута выполняется элементом `button`. Смена маршрута выполняется ссылкой.

Текст интерфейса пишется на русском.

## shadcn

Компоненты shadcn лежат в `src/presentation/components/ui`. Тема задаётся CSS-переменными в `src/app/globals.css`. Общий вариант оформления добавляется через `variant` или `size`.

## Стили

Компоненты экранов стилизуются по БЭМ в CSS-модуле рядом с компонентом. Классов Tailwind и атрибута `style` на их разметке нет.
В `src/app/globals.css` кроме темы shadcn лежат сброс и правила, без которых shadcn не работает.

Один компонент — один блок — один `*.module.css`. Имя блока — имя компонента в kebab-case.

Пример. `MessageList` соответствует блоку `message-list`.

```css
.message-list {
    display: flex;
    flex-direction: column;
}

.message-list__item {
    padding: 12px 16px;
}

.message-list__item--unread {
    font-weight: 600;
}
```

```tsx
import clsx from 'clsx'

import styles from './MessageList.module.css'

type MessageListItemProps = {
    title: string
    isUnread: boolean
}

export function MessageListItem({title, isUnread}: MessageListItemProps) {
    return (
        <li
            className={clsx(
                styles['message-list__item'],
                isUnread && styles['message-list__item--unread'],
            )}
        >
            {title}
        </li>
    )
}
```

Класс в модуле записывается полным именем БЭМ и берётся из `styles` через квадратные скобки. Несколько классов соединяет
`clsx`.

Элемент — часть блока без самостоятельного использования: в примере это `__item`. Модификатор — вариант или состояние: в
примере это `--unread`. Модификатор добавляется к классу блока или элемента и не заменяет его.

Вложенный элемент не объявляется. Если у элемента появляются собственные части, объявляется новый блок. Пример:
`__title` и `__meta` принадлежат блоку `message-list-item`, а не элементу `message-list__item`.

Селектор не привязывается к тегу, id и классам другого блока. В модуле нет `:global`. Внешние отступы компонента shadcn
задаёт блок-обёртка. Селектор снаружи не обращается к внутренней разметке `Button` и `Input`.

## Zustand

Хранилище лежит в `src/presentation/stores`.

Состояние одного компонента и его прямых потомков хранится в `useState`.

Zustand используется, когда одно состояние нужно нескольким частям дерева. Пропсы через всё дерево для этого не проводятся.

Данные, которые рисует только серверный компонент, остаются в нём. Данные запроса, нужные нескольким клиентским компонентам, один раз записываются в хранилище на границе `layout`. Маршрут в хранилище не кладётся.

Файл экспортирует хук. Имя начинается с `use` и заканчивается на `Store`. Состояние и действия описаны одним типом. TSX
и компонентов в хранилище нет.

Пример хранилища сессии.

```ts
import {create} from 'zustand'

type SessionState = {
    userId: string | null
    setUserId: (userId: string | null) => void
}

export const useSessionStore = create<SessionState>((set) => ({
    userId: null,
    setUserId: (userId) => set({userId}),
}))
```

Компонент берёт из хранилища селектором только нужные поля, а не весь стейт.

Пример селектора.

```tsx
const userId = useSessionStore((state) => state.userId)
```

Хранилище импортируют только клиентские компоненты. Пароль после отправки запроса не хранится. 
Токен сессии записывает сервер в `httpOnly`-cookie, JavaScript его не читает. 
Ключ конкретной операции остаётся в состоянии формы и передаётся аргументом метода сервиса.

Отдельная область интерфейса получает отдельное хранилище. Пример областей: сессия, черновик сообщения. Общего хранилища
на приложение нет.

## Импорты

Импорт внутри `src` идёт через алиас `@/`. Относительный импорт остаётся для файлов той же папки: CSS-модуль и соседний
компонент.

Группы разделяются пустой строкой:

1. внешние пакеты;
2. импорты из `@/` от слоя бизнес-логики к модулю файла;
3. относительные импорты;
4. CSS-модуль.

Тип, используемый только как тип, импортируется через `import type`.

## Форматирование

Форматирование задаёт конфигурация Prettier и ESLint. Пока конфигурации нет:

- отступ — два пробела;
- одинарные кавычки;
- точка с запятой в конце оператора;
- висячая запятая там, где её допускает синтаксис.

## Документация

Документация пишется на русском в Markdown. Имена файлов, типов, маршрутов и эндпоинтов пишутся так же, как в коде.

Заголовок первого уровня один. Дальше `##` и `###`. Одно правило — абзац. Шаги и перечисления — список. Однотипные сведения сводятся в таблицу. Ссылка на файл в репозитории даётся путём в обратных кавычках.

Правило формулируется один раз. Фрагмент кода в документе — пример, перед ним стоит слово «Пример». Реализация, которой ещё нет, в документе не расписывается.
