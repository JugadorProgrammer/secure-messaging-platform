# Работа с репозиторием

В репозитории находятся сразу четыре решения: COORD, FRONT, CRYPTO и AUTH.
Каждое решение целиком лежит в своей линии веток.

## Решения

| Код    | Решение                  | Стабильная ветка | Ветка разработки | Название docker-image |
|--------|--------------------------|------------------|------------------|-----------------------|
| COORD  | координационный сервис   | `COORD-master`   | `COORD-develop`  | `smp-coord`           |
| FRONT  | визуальный интерфейс     | `FRONT-master`   | `FRONT-develop`  | `smp-front`           |
| CRYPTO | криптографический сервис | `CRYPTO-master`  | `CRYPTO-develop` | `smp-crypto`          |
| AUTH   | сервис аутентификации    | `AUTH-master`    | `AUTH-develop`   | `smp-auth`            |

## Ветки

Линии начинаются от `main` и дальше не сходятся. 

`COORD-master`, `FRONT-master`, `CRYPTO-master`, `AUTH-master` являются мастер-ветками своих решений и друг в друга не вливаются. 
Обратно в `main` тоже не вливаются. `main` отведена под общую информацию для всех проектов и отчёты.

Прямых коммитов в `main`, `*-master` и `*-develop` быть не должно. Изменение попадает туда только pull request-ом после
прохождения тестов и ревью.

Ветки решений должны ответвлять от себя только ветки со своими префиксами. Имя ветки лучше всего задавать по префиксу решения и номеру задачи,
и кратко описывать, с чем связана задача.

Пример: Задача "COORD-1. Подготовить эндпоинт выгрузки сообщений" - ветка `COORD-1-get-messages-endpoint`.

`<SOLUTION>-master` — стабильная линия одного решения. Сюда вливается только `<SOLUTION>-develop` стабильной версии.

`<SOLUTION>-develop` — активная разработка этого решения. После влития пайплайн прогоняет тесты, публикует образ для тестового стенда на Docker Hub 
и деплоит его на test-окружение.

Feature-ветки ответвляются от актуального `<SOLUTION>-develop`. Одна ветка — один билет.

Иногда бывают ситуации, когда одна задача вытекает из другой - разрешается продолжить разработку зависимой feature из первой feature-ветки.
Имя ветки необходимо в таком случае двумя номерами, к примеру `COORD-11-15-...`.
После влития ветка удаляется.

На случай срочных исправлений ответвление выполняется от `<SOLUTION>-master`, вливается в него, затем этот же master вливается в свой
`<SOLUTION>-develop`. Именуют такие ветки `<SOLUTION>-hotfix`.

### Пример ветвления

```
main
├── COORD-master
│   └── COORD-develop
│       └── COORD-1-get-messages-endpoint
├── FRONT-master
│   └── FRONT-develop
├── CRYPTO-master
│   └── CRYPTO-develop
└── AUTH-master
    └── AUTH-develop
```

### Локальная разработка

У приложения должен быть профиль `local` для разработки на машине. В репозитории у профиля только безопасные значения по
умолчанию: localhost, фиктивные пароли, локальные порты. Паролей, токенов, закрытых ключей и действительных строк подключения в
коммитируемом профиле нет.

Для локальной разработки каждому контексту необходимо написать свой docker-compose.yml - для поднятия необходимой инфраструктуры.

Секреты и настройки для локального развёртывания можно размещать в `.env`, `appsettings.json`, `.yml`, `.properties`, `.yaml`.


### Развёртывание

CI/CD для тестов и сборки образа с отправкой в Docker Hub должно быть размещено для каждого решения в свой `.github/workflows`.

На feature-ветках пайплайн только прогоняет тесты своего решения. Образ в Docker Hub с feature-ветки не пушится.

Для веток develop и master необходимо подготовить CI/CD-пайплайн c развёртыванием на окружениях: test(для develop), stable (для master).

Пример полного имени образа для пуша в Docker Hub: `<DOCKERHUB_USERNAME>/smp-<solution>`. `DOCKERHUB_USERNAME` заполняется из secrets в Github.

Секреты для test/stable должны храниться в настройках репозитория в 
`settings` -> вкладка `security and quality` -> `secrets and variables` -> `actions`.

## Коммиты

Содержание коммитов должно содержать префикс приложения, номер задачи и краткое описание изменений.

```
<SOLUTION>-<TASKNUM>. <что сделано>
```

Примеры:

```
COORD-1. Добавлен эндпоинт получения сообщений
```

```
AUTH-4: Изменён CI-CD пайплайн.
```

## Pull request и ревью

Общий алгоритм:

1. Автор пушит ветку и открывает PR.
2. Пайплайн этой линии запускает тесты. Пока проверка `test` красная или ещё идёт, ревью не начинается.
3. После пройденных тестов ревьюер смотрит PR. Нужно одно одобрение; автор своё PR не одобряет.
4. Влитие доступно, когда тесты пройдены, одобрение есть и замечания ревью закрыты.
5. Новый коммит в ветку заново запускает тесты и снимает прежнее одобрение.

Ревьюер проверяет:

- в изменениях нет секретов и реальных учётных данных;
- поведение покрыто тестами этого решения;
- смена контракта названа в описании PR;
- соответствие соглашению по написанию кода styleguide.md.
