# AUTH — соглашения по коду и документации

> **Статус:** Draft v0.1 — предложение для командного обсуждения.  
> **Задача:** AUTH-3, [Issue #63](https://github.com/JugadorProgrammer/secure-messaging-platform/issues/63).  
> **Предполагаемый стек первой итерации:** C++20, CMake, CTest. **Стек не утверждён командой.**

## 1. Назначение и область действия

Документ задаёт предварительные соглашения по написанию, оформлению, тестированию и документированию кода сервиса аутентификации AUTH.

- Правила относятся только к решению AUTH и не изменяют соглашения других решений (`COORD`, `FRONT`, `CRYPTO`).
- Процесс создания веток, коммитов и Pull Request регламентируется общим [`gitflow.md`](../gitflow.md). Этот документ его дополняет, но не дублирует.
- Для нового кода действуют согласованные правила этого документа; изменения правил обсуждаются через Pull Request.
- До утверждения языка и архитектуры описанные ниже технологические решения являются **предложением**, а не обязательным стандартом.

## 2. Технологический стек (предложение)

| Область | Предлагаемый выбор | Статус |
|---|---|---|
| Язык | C++20 | Обсудить |
| Система сборки | CMake | Обсудить |
| Компилятор | MSVC в Visual Studio; при необходимости Clang/GCC | Обсудить |
| Форматирование | `clang-format`, единый `.clang-format` в ветке AUTH | Обсудить |
| Статический анализ | `clang-tidy`, предупреждения компилятора | Обсудить |
| Тестирование | CTest + выбранный командой фреймворк (например, GoogleTest) | Обсудить |
| API/транспорт | Не определён; согласовать с COORD и FRONT | Открытый вопрос |
| Хранение пользователей | Не определено; согласовать границы AUTH/COORD | Открытый вопрос |

При выборе иного стека соответствующие разделы должны быть пересмотрены отдельным коммитом или PR.

## 3. Общие принципы разработки

1. **Одна ответственность на модуль.** Проверка пароля, OTP, управление сессиями, роли и работа с хранилищем разделяются логически.
2. **Явные зависимости.** Не использовать скрытые глобальные состояния и синглтоны там, где зависимость можно передать через конструктор или параметр.
3. **Минимум дублирования.** Повторяемая логика выделяется в самостоятельную функцию или класс, если это улучшает читаемость.
4. **Безопасные значения по умолчанию.** При ошибке проверки, отсутствии роли или недоступности зависимости доступ запрещается.
5. **Тестируемость.** Бизнес-логика должна проверяться без запуска пользовательского интерфейса; взаимодействие с внешними сервисами подменяется тестовыми реализациями.
6. **Изменение контракта — явно.** Публичные интерфейсы AUTH меняются только с обновлением документации и согласованием зависимых компонентов.

## 4. Предлагаемая структура каталогов

Ниже приведена **примерная**, не утверждённая структура C++-решения. Она не требует немедленно создавать все каталоги в рамках AUTH-3.

```text
include/auth/             публичные заголовки и типы AUTH
src/                      реализация сервиса
src/account/              регистрация и операции с учётными записями
src/password/             проверка и смена паролей
src/otp/                  проверка одноразовых кодов
src/session/              управление сессиями
src/access/               роли и проверки полномочий
tests/                    модульные и интеграционные тесты
docs/styleguide.md        настоящее соглашение
docs/contracts.md         контракты взаимодействия (отдельное согласование)
CMakeLists.txt            конфигурация сборки
```

Бизнес-логика не должна зависеть от конкретного UI, HTTP-фреймворка или СУБД. Интеграционные адаптеры добавляются после утверждения архитектуры.

## 5. Именование и форматирование C++

### 5.1. Именование

Предлагается единый стиль:

| Сущность | Правило | Пример |
|---|---|---|
| Файл | `snake_case` | `password_service.cpp` |
| Класс/структура/enum | `PascalCase` | `AuthService`, `UserRole` |
| Функция/метод | `snake_case` | `verify_password()` |
| Локальная переменная | `snake_case` | `user_id` |
| Поле класса | `snake_case_` | `session_store_` |
| Константа | `kPascalCase` | `kMaxLoginAttempts` |
| Пространство имён | нижний регистр | `auth`, `auth::otp` |
| Макрос | `UPPER_SNAKE_CASE` | `AUTH_ENABLE_TESTS` |

Избегать сокращений, смысл которых не очевиден: `user_id` лучше `uid`, если контекст неоднозначен. Названия должны отражать назначение, а не тип (`sessions`, а не `sessions_vector`).

### 5.2. Форматирование

- Отступ: 4 пробела, без табуляции в исходниках.
- Открывающая фигурная скобка для функций, классов и управляющих конструкций — на той же строке (предварительное предложение).
- Использовать `#pragma once` в заголовках (предварительное предложение).
- Заголовки должны включать только необходимые зависимости; предпочтительно использовать предварительные объявления, когда они достаточны.
- Форматирование автоматически выполняется `clang-format`; стилистические споры решаются изменением общего `.clang-format`, а не ручным форматированием.

Пример:

```cpp
namespace auth {

class SessionService {
public:
    bool is_active(std::string_view session_id) const;

private:
    std::string current_session_id_;
};

}  // namespace auth
```

Фрагмент иллюстрирует только оформление, а не реальный контракт сервиса.

## 6. Современный C++ и управление ресурсами

- Предпочитать RAII: ресурс должен освобождаться при выходе объекта из области видимости.
- Не использовать ручное `new`/`delete` для обычного владения памятью; предпочтительны стандартные контейнеры и `std::unique_ptr` при необходимости динамического владения.
- Передавать крупные неизменяемые объекты по `const&` или `std::string_view`, учитывая время жизни данных; для небольших значений использовать передачу по значению.
- Указывать `const` для методов и данных, которые не должны изменяться.
- Использовать `enum class` вместо неограниченных перечислений там, где это применимо.
- Не применять небезопасные преобразования типов и операции с памятью без необходимости и обоснования.
- Исключить неопределённое поведение; предупреждения компилятора не игнорировать без объяснения.

## 7. Обработка ошибок и результаты операций

- Ошибки пользователя, сбои хранилища и внутренние ошибки должны различаться логически.
- Недопустимые входные данные не должны приводить к аварийному завершению программы.
- Обработчик API не должен возвращать детали внутренней реализации, трассировки или секреты.
- Способ передачи ошибок между слоями (`std::expected` в C++23, собственный `Result`/типизированные ошибки или исключения) **должен быть согласован отдельно**; для C++20 нельзя полагаться на доступность `std::expected`.
- При ошибках аутентификации не раскрывать лишние сведения о существовании учётной записи.
- При сбое проверки прав доступ не предоставляется.

Формат внешних ошибок и HTTP-коды определяются совместно с COORD и FRONT в документе контрактов, а не произвольно внутри реализации AUTH.

## 8. Правила безопасности

- Пароли и ответы на секретные вопросы не хранятся в открытом виде. Для паролей требуется стойкая функция формирования парольных хешей с уникальной солью; алгоритм и допустимые зависимости нужно согласовать отдельно.
- Реальные пароли, ключи, токены, OTP-секреты и данные подключения не добавляются в Git и не выводятся в лог.
- Учётные данные тестового окружения должны быть фиктивными; конфигурации с секретами исключаются из отслеживания Git.
- OTP имеют ограниченный срок действия; повторное применение ранее принятого кода должно отклоняться в соответствии с согласованной схемой.
- Полная авторизованная сессия создаётся только после успешного завершения всех предусмотренных этапов входа.
- Проверки доступа выполняются на серверной стороне. Скрытие элемента интерфейса не считается разграничением прав.
- Ролевые полномочия проверяются для каждой защищённой операции, в том числе при обращении напрямую к API.
- Сравнение чувствительных кодов и токенов должно учитывать защиту от утечек по времени; конкретную реализацию согласовать отдельно.
- Не разрабатывать собственный алгоритм хеширования паролей или генерации криптографически стойких случайных чисел без отдельного требования и согласования.

**Открытый вопрос:** исходное ЧТЗ описывает третий фактор как код от отдельного генератора по времени, а часть FRONT-задач — как код восстановления. Механизм требуется согласовать до реализации.

## 9. Логирование

Журнал может содержать: время события, тип операции, технический идентификатор запроса, идентификатор учётной записи (если известен) и результат операции.

Не логировать: пароли, ответы на секретные вопросы, OTP-коды, секреты их генерации, токены сессий, закрытые ключи и полные тела чувствительных запросов.

События регистрации, успешного и неуспешного входа, смены и восстановления пароля желательно оформлять единообразно. Состав полей и ответственный за общее журналирование согласуются с COORD.

## 10. Тестирование

- В `tests/` размещаются автоматические тесты с понятными именами и независимыми тестовыми данными.
- Для каждого публичного сценария должны быть успешные и отрицательные проверки.
- Обязательные примеры: повторная регистрация логина, неверный пароль, неверный или просроченный OTP, повторное использование OTP, отказ в доступе к чужим ресурсам, смена и восстановление пароля.
- Тесты не должны обращаться к реальной почте и использовать действительные учётные данные.
- Общий запуск тестов должен быть задокументирован после утверждения инструментов; в предлагаемом стеке это `ctest --test-dir build --output-on-failure` после настройки сборки.
- Изменение функциональности сопровождается тестами; исправление дефекта — тестом, воспроизводящим дефект.

## 11. Документация и взаимодействие между сервисами

- Документация в `docs/` ведётся в Markdown и на русском языке. Имена типов, функций и API-полей — на английском.
- Комментарии объясняют **почему** принято решение, а не пересказывают очевидные операции.
- Публичные классы, нестандартные ограничения и неочевидные инварианты документируются.
- Для API отдельно фиксируются путь, метод, авторизация, структура запроса, структура ответа, коды ошибок и примеры.
- Контракты AUTH с COORD и FRONT должны быть согласованы до параллельной реализации зависимых компонентов.
- Изменения внешнего поведения и форматов данных отражаются в документации в том же PR.

## 12. Проверки в CI (предложение)

Для feature-веток AUTH предлагается запускать:

1. Конфигурацию проекта через CMake.
2. Сборку в выбранной конфигурации.
3. Проверку форматирования (`clang-format`).
4. Статический анализ по согласованным правилам.
5. Автоматические тесты через CTest.

Публикация контейнера и развёртывание на тестовом окружении не выполняются из feature-веток — согласно `gitflow.md`. Реализация CI относится к отдельной задаче, если это не согласовано иначе.
