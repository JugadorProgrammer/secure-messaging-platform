# Соглашения по коду и документации

Документ фиксирует правила написания кода и текста в координационном сервисе. Он не
претендует на оригинальность: почти всё здесь уже сформулировано в признанных руководствах
по Go и в стандартах, на которые эти руководства опираются. Наша задача — выбрать
из них то, что применимо к нашему сервису, и явно отметить места, где мы сознательно
поступаем иначе.

Правила без объяснения причины соблюдаются ровно до первого спора. Поэтому у каждого
раздела есть ссылка на источник и, где нужно, короткое обоснование.

## 1. Статус документа

Документ дополняет `gitflow.md`, который описывает ветки, коммиты и порядок ревью.
Пересечений немного: `gitflow.md` отвечает на вопрос «как изменение попадает в основную
ветку», этот документ — «как должно выглядеть изменение».

Соглашения обязательны для нового кода. Существующий код приводится к ним по мере правок,
отдельным рефакторингом ради соответствия гайду не занимаемся.

Если правило мешает в конкретном месте, это обсуждается в PR. Решение, которое
повторяется, вносится сюда отдельным изменением. Молча отступать не нужно: читающий
не обязан угадывать причину.

### 2.2. Порядок приоритета

Когда источники расходятся, действует такой порядок:

1. Поведение, зафиксированное в `contracts.md`. Это наш собственный контракт,
   он важнее общих рекомендаций.
2. Требования стандартов и RFC, если речь о протоколе.
3. Go Code Review Comments и Google Go Style Guide.
4. Uber Go Style Guide.
5. Этот документ в части, которая уточняет перечисленное.

Обратный порядок тоже встречается: если гайд противоречит контракту, правится гайд,
а не контракт. Контракт меняется только через отдельный PR.

### 2.3. Язык

Код, имена, комментарии и сообщения внутренних ошибок — на английском. Это следствие
того, что весь инструментарий, документация библиотек и примеры в интернете
англоязычные, и смешивать два языка в одном файле неудобно.

Тексты, которые видит пользователь, — на русском. Это требование продукта, а не
техническое решение, поэтому исключение делается только для слоя, который формирует
ответ клиенту.

Документация проекта — на русском, потому что её читает команда.

## 3. Базовые принципы

Три идеи из Effective Go и Go Proverbs, которые объясняют большинство частных правил.

**Явное лучше неявного.** Код должен читаться сверху вниз без обращения к другим файлам.
Если для понимания строки нужно знать, что где-то в другом пакете есть побочный эффект,
это плохая строка.

**Простота важнее общности.** Обобщённое решение, у которого один потребитель, стоит
дороже прямой реализации и почти всегда оказывается не тем. Абстракция вводится, когда
появился второй потребитель, а не в расчёте на него.

**Ошибки — это значения.** Они возвращаются, проверяются и оборачиваются, а не
превращаются в панику или в лог с продолжением работы.

Из этого следует практическое: мы не спорим о вкусах там, где есть измеряемый критерий.
Читаемость, количество веток, размер функции, число зависимостей — обсуждаемо.
«Мне так больше нравится» — не аргумент, но и не запрет: вкус иногда отражает опыт,
который трудно сформулировать.

## 4. Структура и зависимости

### 4.1. Пакеты

Раскладка описана в `contracts.md`, раздел 1. Принципы, из которых она выросла,
совпадают с рекомендациями Google Go Style Guide.

Пакет отвечает на один вопрос. `internal/store` — где лежат данные, `internal/auth` —
кто пришёл и что ему можно, `internal/messages` — что делать с сообщением. Пакет,
отвечающий на два вопроса, делится.

Имя пакета — существительное в единственном числе, короткое, без префиксов:
`store`, `auth`, `verify`. Имена `utils`, `helpers`, `common`, `models` запрещены.
Причина не в эстетике: пакет с таким именем через полгода содержит всё подряд, и его
невозможно ни описать одной строкой, ни удалить.

Имя пакета не дублируется в именах его сущностей. `store.Store` допустим, потому что
это тип-фасад; `store.StoreMessage` — нет, достаточно `store.Message`.

### 4.2. Интерфейсы

Интерфейс объявляется у потребителя, а не у реализации. Это правило из Go Code Review
Comments, и оно у нас не обсуждается: именно оно позволяет тестировать `internal/auth`
без Postgres и без запуска Крипто-модуля.

Практическое следствие: `internal/ports` содержит интерфейсы, которые нужны нескольким
пакетам. Локальные интерфейсы на одну-две функции объявляются прямо в пакете-потребителе.

Возвращаем конкретный тип, принимаем интерфейс. Функция, возвращающая интерфейс
без причины, лишает вызывающего доступа к остальным методам и затрудняет отладку.

Интерфейс на десять методов почти всегда означает, что потребителю нужна не вся
поверхность. Если такое происходит, интерфейс делится по назначению.

### 4.3. Зависимости

Внешние зависимости добавляются осознанно. На сегодня согласованы две: драйвер Postgres
и библиотека для PDF. Всё остальное — стандартная библиотека.

Новая зависимость обсуждается в PR: какую задачу решает, что даёт по сравнению
со стандартной библиотекой, кто её поддерживает, как выглядит отказ от неё. Довод
«так короче» не принимается, довод «в стандартной библиотеке этого нет» принимается.

Циклический импорт — сигнал, что границы проведены неверно. Лечится пересмотром
ответственности, а не выносом общего кода в третий пакет.

## 5. Именование

Основа — Google Go Style Guide и раздел Naming из Go Code Review Comments.

`MixedCaps`, без подчёркиваний. Имя отражает смысл, а не тип: `users`, а не `userSlice`;
`count`, а не `intCount`. Длина имени пропорциональна области видимости: `i` в цикле
нормально, `userIdentifierWhichCameFromToken` в параметре — нет.

Аббревиатуры пишутся одинаково в регистре: `userID`, `httpClient`, `parseURL`.
Не `userId`, не `HttpClient`.

Функция называется по действию. `SetMethodEnabled`, `EnsureUserKey`, `Parse`.
Возвращаемое значение не дублируется в имени: `Methods`, а не `GetMethodsList`;
`New`, а не `CreateNew`.

Переменные с секретами называются так, чтобы это было видно: `masterKey`, `privatePEM`,
`token`. Не `key`, не `data`, не `s`.

Булевы значения читаются как утверждение: `enabled`, `ready`, `hasAccess`.
Отрицания избегаем: `notReady` в условии `if !notReady` требует лишнего шага.

## 6. Ошибки

Раздел опирается на Effective Go, Go Code Review Comments и раздел Errors
из Uber Go Style Guide. Отличия касаются только сентинельных ошибок, о них ниже.

### 6.1. Возврат и обёртка

Ошибка возвращается последним значением, проверяется сразу. Обёртка — через `%w`,
проверка — через `errors.Is` и `errors.As`. Сравнение текста ошибки в коде запрещено:
текст меняется, поведение — нет.

```go
msg, err := s.store.GetMessage(ctx, id)
if err != nil {
    if errors.Is(err, ports.ErrNotFound) {
        return httpx.ErrNotFound
    }
    return fmt.Errorf("get message %d: %w", id, err)
}
```

Добавлять контекст нужно один раз, на границе пакета. Цепочка из пяти `%w`
с одинаковым текстом бесполезна: она не помогает найти причину.

### 6.2. Тексты

Текст ошибки — с маленькой буквы, без точки в конце, без слова «ошибка»:
`failed to load message`, а не `Error: Failed to load message.`. Правило из Go Code
Review Comments, соблюдается буквально.

Текст не содержит входных данных, если они могут быть чувствительными.
`invalid key: <PEM>` — плохая ошибка, `invalid key: not a PEM block` — хорошая.

Пользователю уходит отдельный текст на русском, заданный в `writeErr`. Внутренняя
ошибка остаётся в логе. Клиент не должен видеть ни имена таблиц, ни адреса сервисов,
ни текст ответа Крипто-модуля.

### 6.3. Сентинельные ошибки

Здесь мы отступаем от распространённой рекомендации объявлять ошибки там, где они
возвращаются. У нас сентинельные значения лежат в `internal/ports`, потому что
их возвращает одна реализация, а проверяет другая, и обе стороны не должны зависеть
друг от друга.

Компромисс осознанный: глобальные значения создают связность, но альтернатива —
импорт `internal/store` из `internal/auth` ради сравнения ошибки — хуже.

Ошибки, которые не пересекают границу пакета, объявляются на месте.

### 6.4. Паника

`panic` не используется для управления потоком. Допустим только там, где продолжение
невозможно: при инициализации, при нарушении инварианта, который не должен нарушаться
никогда. Всегда с осмысленным сообщением.

Перехват паники в HTTP-слое есть, но это страховка от падения процесса, а не рабочий
механизм. `http.ErrAbortHandler` при перехвате пробрасывается дальше: его использует
`httputil.ReverseProxy` для обрыва соединения.

## 7. Контекст

Правила взяты из документации пакета `context` и из статьи Go Blog «Contexts and Structs».

`context.Context` — первый параметр функции, всегда. В структуре не хранится,
через глобальные переменные не передаётся.

Таймаут ставится на каждой границе, где ждём внешний ответ: сервис учётных записей,
Крипто-модуль, база. Значения по умолчанию — в конфигурации, не в виде чисел в коде.

Отмена контекста не превращается в `500` и не логируется как ошибка. Клиент ушёл,
это нормальная ситуация.

Для фоновых операций, которые должны дожить до конца после ответа клиенту — запись
в журнал, генерация ключа — используется `context.WithoutCancel` с собственным таймаутом.
Иначе отмена запроса браузером обрывает работу, которую уже некому повторить. Это
не описано в стандартной документации явно, но прямо следует из семантики отмены.

## 8. HTTP-слой

Семантика методов, кодов состояния и заголовков — по RFC 9110. Передача токена —
по RFC 6750, схема `Bearer`.

Маршруты регистрируются паттернами стандартного мультиплексора: `"GET /api/messages/{id}"`.
Возможность появилась в Go 1.22, и на нашем наборе путей сторонние роутеры не добавляют
ничего, кроме зависимости.

Один хендлер делает одно: разбирает запрос, вызывает сервис, пишет ответ. Бизнес-логика
в хендлере не живёт — её нельзя переиспользовать и трудно тестировать.

Ответ всегда JSON, включая ошибки. `http.Error` не используем: он отдаёт `text/plain`,
и клиент вынужден разбирать два формата. Исключений нет, включая `405`, `413` и `500`.

Формат тела ошибки — `{"error":{"code","message"}}`. Здесь мы отступаем от RFC 7807
(Problem Details), который предлагает `application/problem+json` с полями `type`,
`title`, `status`, `detail`. Причина: формат зафиксирован в контракте с интерфейсом
и уже реализован на другой стороне. Отступление записано явно, чтобы при чтении
не возникало вопроса, почему не по стандарту.

Тело запроса ограничивается по размеру до чтения. Заголовки проверяются до разбора тела.
Валидация возвращает первую проблему с понятным текстом, а не список из десяти пунктов.

Заголовки ответа: `Content-Type` с кодировкой, `Cache-Control: no-store` для всего,
что содержит данные пользователя, `X-Content-Type-Options: nosniff` для JSON.
Для файлов — `Content-Disposition` и точный `Content-Length`.

## 9. Конфигурация и секреты

Конфигурация читается из окружения — принцип III из Twelve-Factor App. Значения
по умолчанию допустимы только для локальной разработки и только безопасные.

Конфигурация валидируется при старте. Отсутствие обязательного параметра — ошибка
запуска с ненулевым кодом возврата, а не падение при первом запросе.

Мастер-ключ проверяется на длину и кодировку при старте, хранится массивом байт,
а не строкой, и не печатается. Структура конфигурации, попавшая в лог целиком,
не должна раскрывать ни мастер-ключ, ни строку подключения.

Требования к работе с секретами — по OWASP ASVS, раздел про управление секретами.
Коротко: не логировать, не возвращать клиенту, не хранить в открытом виде,
не включать в сообщения об ошибках, не коммитить.

Закрытые ключи расшифровываются только на время операции. После использования буфер
обнуляется. Это защита от дампа памяти и от логов, которые иногда собирают больше,
чем предполагалось.

Секреты не попадают в тесты. В фикстурах — заведомо недействительные значения,
сгенерированные на месте. Реальный ключ в тесте означает, что его придётся менять
при каждой ротации, и однажды кто-нибудь закоммитит боевой.

## 10. Логирование

Логи — поток событий, а не файл с отчётом: принцип XI из Twelve-Factor App.
Формат — структурированный, через `log/slog`.

Обязательные поля записи о запросе: метод, путь, статус, длительность,
идентификатор запроса. Пользователь — если известен.

Не логируются: тело запроса и ответа на путях аутентификации, заголовок `Authorization`,
`Cookie`, токены, ключи, тексты сообщений, мастер-ключ. Это требование OWASP ASVS
к логированию, и оно не смягчается даже для отладки: временное живёт дольше, чем кажется.

Уровни используются по назначению. `Error` — ситуация, требующая внимания человека.
`Warn` — отклонение, с которым сервис справился. `Info` — значимые события жизненного
цикла. `Debug` — диагностика, которая в рабочей конфигурации выключена.

Сообщение лога пишется на английском, поля — в нижнем регистре с подчёркиваниями.

## 11. Тесты

Формат и требования — из Go Code Review Comments, раздел Test Tables, и из документации
пакета `testing`.

Тесты обязательны на всё, что имеет поведение: хендлеры, сервисы, разбор и сборка
форматов. На тривиальные геттеры — по желанию.

Табличный формат: срез структур с именем случая, входом и ожиданием. Он даёт
возможность добавлять сценарии одной строкой и видеть в отчёте, какой именно случай
упал. Вложенные таблицы и генераторы тестов не используем: на нашей кодовой базе
они усложняют чтение без выигрыша.

Имя случая — по-русски или по-английски, но одинаково в пределах файла. Чаще по-русски:
`"нет токена"`, `"сессия неполная"`. В отчёте читается лучше, чем `test case 3`.

Вспомогательные функции помечаются `t.Helper()`, иначе в отчёте будет строка внутри
хелпера вместо места вызова. Освобождение ресурсов — через `t.Cleanup()`, а не через
`defer` в теле теста: `Cleanup` выполняется и при падении через `t.Fatal`.

Внешние сервисы подменяются `httptest.Server`, а не моками HTTP-клиента: так проверяется
реальная сериализация, включая заголовки и тело. Заглушки хранилища и крипто-клиента —
маленькие структуры с функциональными полями, объявленные в тестовом файле.

Тест не зависит от порядка запуска и от общего состояния. Тестовая база чистится
перед каждым случаем. Тест, который проходит только при запуске всего пакета целиком,
считается сломанным.

Тесты с внешней инфраструктурой помечаются build-тегом и пропускаются через `t.Skip`,
если переменная с подключением не задана. Иначе локальный `go test ./...` падает у всех,
у кого не поднят Postgres.

Проверяем не только успех. Для каждой ветки с ошибкой — отдельный случай, особенно
для тех, где легко получить неверный код ответа: недоступность внешнего сервиса,
неверный ключ, чужой ресурс.

## 12. Комментарии и godoc

Правила — из Effective Go и раздела комментариев Google Go Style Guide.

Комментарий объясняет причину, а не действие. `// increment counter` бесполезен;
`// счётчик считает попытки, а не успехи: лимит расходуется и на неудачных входах`
полезен. На английском.

Doc-комментарий экспортируемой сущности начинается с её имени и образует законченное
предложение:

```go
// MethodEnabled reports whether the encryption method is enabled.
// An unknown code is reported as disabled, not as an error.
func MethodEnabled(ctx context.Context, store ports.Store, code string) (bool, error)
```

Пустая строка между предложением-сводкой и остальным текстом разделяет краткое
описание и детали. Это позволяет инструментам показывать только первую строку.

Закомментированный код не храним. История есть в git, и она точнее любого комментария.

## 13. Документация

### 13.1. Структура

Документация строится по Diátaxis: четыре типа документов, у каждого своя задача.

| Тип | Что это | Пример у нас |
|---|---|---|
| Справочник | точные факты, без объяснений | `contracts.md` |
| Объяснение | почему так устроено | этот документ, разделы 2 и 3 |
| Инструкция | как выполнить задачу | `README.md`, раздел запуска |
| Учебный материал | введение для нового человека | `coordination-brief.md` |

Смешивать типы в одном файле можно, но тогда нужно понимать, что читатель ищет,
и не прятать справочную таблицу в середине рассуждения.

### 13.2. Файлы и имена

Документы лежат в `docs/`. Имена — строчными буквами, слова через дефис, расширение `.md`:
`contracts.md`, `work-plan.md`, `styleguide.md`.

Документ по конкретной роли или подсистеме получает префикс: `tz-dev-a.md`.
Версии вида `final`, `final-2`, `new` не используются: версия одна, изменения видны
в истории.

Корневой `README.md` — точка входа: что это за сервис, как поднять, куда смотреть дальше.
Он не дублирует остальные документы, а ссылается на них.

### 13.3. Текст

Стиль — по Google developer documentation style guide, с поправкой на русский язык.

Документ начинается с абзаца, объясняющего назначение: какую проблему решает и для кого
написан. Формулировка «данный документ описывает» считается плохим началом: она
не сообщает ничего, кроме факта существования документа.

Разделы — по смыслу, не больше двух уровней вложенности. Третий уровень почти всегда
означает, что документ пора разделить.

Полужирный — для акцента, не для каждого второго слова. Страница, где всё выделено,
не выделяет ничего.

Списки — там, где действительно перечисление. Если пункты начинаются с «также»,
«кроме того», «важно», это уже текст, и его лучше написать абзацем.

Блоки кода — с указанием языка. Примеры команд — рабочие, скопированные из терминала,
а не восстановленные по памяти.

Не используем эмодзи и восклицательные знаки. Не пишем «просто», «очевидно»,
«как известно»: если очевидно — объяснять не нужно, если не очевидно — обидно читателю.

### 13.4. Требования

Требование формулируется проверяемо. Ключевые слова — по RFC 2119: «должен»,
«не должен», «следует», «может». Они пишутся обычным текстом, без капса: капс
в русском тексте читается как крик, а не как нормативный документ.

«Сервис должен работать быстро» — не требование. «Список из 100 сообщений отдаётся
быстрее 200 мс при прогретой базе» — требование.

У требования есть идентификатор, если на него ссылаются из кода, тестов или других
документов. Идентификаторы не переиспользуются после удаления требования.

Критерий приёмки пишется от результата, а не от процесса. Не «написать тесты
на авторизацию», а «запрос без токена возвращает 401 с кодом unauthorized».
Первое нельзя проверить, второе можно.

Одна задача — один результат. Если в описании появилось «а также», это, скорее всего,
две задачи.

### 13.5. Решения

Архитектурные решения, которые трудно пересмотреть, фиксируются в виде короткой записи
по формату ADR: контекст, решение, последствия. Хранятся в `docs/adr/` с номером
в имени файла.

Запись не нужна для рядовых решений. Нужна там, где через полгода спросят «почему так»,
а ответа в коде нет: выбор формата контейнера подписи, отказ от PAdES, размещение
мастер-ключа, разделение зон ответственности.

## 14. Git

Правила веток, коммитов и ревью — в `gitflow.md`. Три уточнения по формулировкам.

Сообщение коммита отвечает на вопрос, что изменилось для читателя, а не что делал автор.
`COORD-7. Добавлены Authn, Require, /api/me и /api/roles` — хорошо. `COORD-7. fix` —
плохо: по такому сообщению нельзя найти причину изменения через полгода.

Формат `COORD-<номер>. <описание>` отличается от Conventional Commits. Отступление
вынужденное: `gitflow.md` требует префикс решения и номер задачи, а совместить это
с `feat(scope):` без потери читаемости не получается.

Один коммит — одно логическое изменение. Переименование и правка логики в одном коммите
делают дифф нечитаемым.

Описание PR содержит то, чего не видно в диффе: почему сделано именно так, какие
альтернативы отброшены, что осталось за рамками. Если PR меняет поведение — об этом
отдельная строка.

## 15. Сознательные отступления

Сводка мест, где мы поступаем не по общему руководству. Каждое отступление имеет причину
и не должно восприниматься как небрежность.

| Отступление | От чего | Причина |
|---|---|---|
| Тело ошибки `{"error":{"code","message"}}` | RFC 7807 | формат зафиксирован контрактом с интерфейсом |
| Сентинельные ошибки в общем пакете `ports` | совет объявлять ошибки у потребителя | ошибку возвращает одна реализация, проверяет другая |
| Коммит `COORD-7. ...` | Conventional Commits | требование `gitflow.md` |
| Комментарии на английском, документация на русском | единый язык проекта | код читают инструменты и внешние читатели, документы — команда |
| Тексты ошибок для пользователя на русском | общая англоязычность кода | требование продукта |
| Собственный контейнер подписи PDF | PAdES | ограничение Крипто-модуля, зафиксировано в контракте |
| `-race` в каждом прогоне тестов | рекомендация запускать отдельно | гонки в этом сервисе дороже времени сборки |

Список пополняется. Если отступление перестало быть нужным, оно убирается, а не
остаётся «на всякий случай».

## 16. Чек-лист ревьюера

Короткий список того, что проверяется в каждом PR. Он не заменяет чтение кода,
но помогает не забыть очевидное.

По коду:

- имена соответствуют смыслу, аббревиатуры в одном регистре;
- нет пакетов `utils` и `helpers`;
- интерфейсы объявлены у потребителя;
- ошибки обёрнуты через `%w` и проверяются через `errors.Is`;
- `context` первый параметр, таймауты на границах;
- паники нет вне инициализации;
- нет `http.Error` и текстовых ответов на ошибку;
- секреты не попадают в лог, ответ и сообщение об ошибке.

По тестам:

- новое поведение покрыто, включая ошибочные ветки;
- табличный формат, имена случаев читаемые;
- внешние сервисы через `httptest`, а не через моки клиента;
- инфраструктурные тесты пропускаются без переменной окружения;
- тесты не зависят от порядка запуска.

По процессу:

- ветка от актуального `COORD-develop`;
- сообщение коммита по формату;
- изменение контракта названо в описании PR;
- README обновлён, если появились новые переменные или маршруты.
