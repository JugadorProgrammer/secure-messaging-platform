# План работ: координационный сервис (COORD)

Документ определяет состав работ, порядок выполнения и критерии приёмки. Технические
детали — типы, форматы, коды ошибок — здесь не дублируются, они зафиксированы
в `contracts.md` и в требованиях к сервису.

## 1. Границы документа

План отвечает на три вопроса: что делаем, в каком порядке, по каким признакам принимаем
результат. Он не заменяет техническое задание и не описывает, как именно реализуется
каждая функция.

## 2. Исходное состояние

В репозитории `secure-messaging-platform` на сегодня есть:

- `main` с `gitflow.md` и пустым README;
- ветка `COORD-1-prepare-requirements` с иерархией требований к сервису;
- ветка `FRONT-master` с требованиями к интерфейсу;
- защищённая `COORD-master`, содержимое которой совпадает с `main`.

Ветки `COORD-develop` нет, кода нет, CI нет. Первый рабочий шаг — не реализация,
а контракты и ветка разработки. Пока их нет, параллельная работа двух человек даст
две несовместимые половины сервиса: разные имена полей, разные сигнатуры хранилища,
разные форматы ошибок.

Входные документы:

| Документ | Роль |
|---|---|
| `coordination-service.md` | требования и сценарии |
| `coordination-brief.md` | краткая версия для смежных команд |
| `coordination-tasks.md` | исходная декомпозиция T1…T15 |
| `contracts.md` | согласованные типы, интерфейсы, форматы |
| `styleguide.md` | соглашения по коду и документации |

При расхождении между `coordination-*.md` и `contracts.md` действует `contracts.md`.

## 3. Порядок работы

Разработка ведётся по `gitflow.md`. Ниже — только то, что влияет на планирование.

Ветки: `COORD-develop` как база, feature-ветка на каждый тикет, влитие через PR после
зелёного пайплайна и одного одобрения. Прямых коммитов в `COORD-develop` и `COORD-master`
нет.

Один тикет — одна ветка — один PR. Если задача вырастает, заводится отдельный тикет,
а не расширяется текущий. Исключение — зависимые задачи: для них допускается ветка
с двумя номерами (`COORD-10-14-...`), это разрешено в `gitflow.md`.

Ревью: автор не одобряет свой PR. Новый коммит снимает одобрение и перезапускает тесты.
Ревьюер проверяет отсутствие секретов, покрытие нового поведения тестами и то, что
изменение контракта названо в описании PR.

Пайплайн на feature-ветке выполняет только проверки решения: `lint`, `test`, `build`.
Публикация образа `smp-coord` и выкладка на стенды — только из `COORD-develop`
(тег `test`) и `COORD-master` (тег `stable`).

Роли. Dev A — шлюз, авторизация, методы шифрования, чтение сообщений, журнал,
проверка подписи. Dev B — хранилище, клиент Крипто-модуля, ключи, шифрование,
расшифрование, PDF, инфраструктура. Границы зон и разделение файлов зафиксированы
в `contracts.md`, раздел 1.

## 4. Этапы

Этапы идут последовательно, внутри этапа задачи выполняются параллельно там, где нет
зависимостей. Оценки приведены в человеко-днях и служат для планирования загрузки,
а не для отчётности.

### Этап 0. Контракты

Одна задача, выполняется совместно: **COORD-2**.

Смысл этапа — зафиксировать то, о чём иначе будут спорить в середине разработки:
доменные типы, интерфейсы хранилища и крипто-клиента, формат запечатывания ключей,
контейнер подписи PDF, правила разбора ответа `introspect`, распределение файлов
между разработчиками.

Результат:

- каталог `internal/ports` с типами и интерфейсами;
- пакеты `internal/sealed` и `internal/pdfsig` с тестами;
- `internal/messages/dto.go` с DTO и преобразованием доменных типов;
- заглушка `internal/api/routes_devb.go`;
- актуальный `contracts.md`;
- `styleguide.md` в ветке разработки.

Приёмка:

- пакеты собираются без реализации хранилища и крипто-клиента, проверяется
  пустым `go build ./...`;
- тесты `sealed` и `pdfsig` проходят, включая негативные сценарии: подмена байта,
  короткий контейнер, мусор после маркера подписи;
- `go vet` и `golangci-lint` чистые;
- PR одобрен обоими разработчиками;
- после мержа остальные тикеты снимаются с пометки `blocked`.

Если на этом этапе выясняется, что Крипто-модуль не предоставляет операции над готовым
хешем, это фиксируется сразу, а не на этапе 3. От ответа зависит формат контейнера
подписи, и переделывать его позже дороже, чем подождать.

### Этап 1. Каркас, хранилище, авторизация

| Тикет | Исполнитель | Оценка, дней |
|---|---|---|
| COORD-3. Каркас сервиса | Dev A | 0.5 |
| COORD-17. Docker, Makefile, CI | Dev B | 1 |
| COORD-4. Схема БД и хранилище | Dev B | 1.5 |
| COORD-5. Клиент Крипто-модуля | Dev B | 1.5 |
| COORD-7. Авторизация, `/me`, `/roles` | Dev A | 1.5 |
| COORD-6. Прокси в сервис учётных записей | Dev A | 0.5 |

Порядок внутри этапа важен: COORD-17 делается сразу после COORD-3, иначе остальные
задачи будут мержиться без проверок. COORD-6 идёт после COORD-7, потому что прокси
`/api/users` использует middleware авторизации.

**COORD-3. Каркас.** Сервис стартует, читает конфигурацию, отдаёт `/health`
и `/api/health`, отвечает ошибками в едином формате, не падает от паники в хендлере
и корректно завершается по сигналу.

Приёмка:

- запуск с пустым окружением даёт внятную ошибку и ненулевой код возврата;
- `/health` и `/api/health` отвечают `200` без обращения к базе и внешним сервисам;
- ошибка валидации и ошибка сервера имеют одинаковую структуру тела;
- паника в тестовом хендлере превращается в `500` без стектрейса в ответе;
- `http.ErrAbortHandler` не перехватывается, иначе ломается прокси;
- мастер-ключ не попадает ни в лог, ни в строковое представление конфигурации;
- покрытие `internal/config` и `internal/httpx` не ниже 80 процентов.

**COORD-17. Инфраструктура.** Образ собирается, контейнер стартует, healthcheck
переходит в состояние `healthy`, пайплайн зелёный на пустом каркасе.

Приёмка:

- `make lint`, `make test`, `make docker` отрабатывают локально;
- в финальном образе нет shell и нет пользователя root;
- healthcheck работает без `curl` и `wget`;
- на feature-ветке не запускаются публикация образа и e2e;
- `.env` в `.gitignore`, секретов в репозитории нет;
- `make test` использует `-race -cover`.

**COORD-4. Хранилище.** Схема создаётся на чистой базе, миграции идемпотентны,
все методы хранилища покрыты тестами на реальном Postgres.

Приёмка:

- повторный старт не ломает схему и не сбрасывает выключенные администратором методы;
- начальные записи методов создаются ровно один раз;
- отсутствие записи отличается от пустого результата отдельной ошибкой;
- список сообщений сортируется по дате и идентификатору, пагинация стабильна;
- анонимная запись в журнал даёт `NULL`, а не ноль;
- запросы параметризованные, конкатенации значений в SQL нет;
- тесты без переменной с DSN пропускаются, а не падают.

**COORD-5. Клиент Крипто-модуля.** Все девять операций вызываются, кодировки соблюдены,
ошибки разделены на неверный ввод и недоступность модуля.

Приёмка:

- каждый эндпоинт покрыт тестом с проверкой тела запроса и разбора ответа;
- ответ `4xx` даёт ошибку неверного ввода, `5xx`, таймаут и обрыв — ошибку недоступности;
- отмена контекста не превращается в ошибку недоступности;
- генерация ключа RSA не обрывается общим десятисекундным таймаутом;
- подпись и проверка идут через операции над готовым хешем;
- на поднятом Крипто-модуле проходит полный цикл: генерация ключей, шифрование,
  расшифрование, хеширование, подпись, проверка подписи.

**COORD-7. Авторизация.** Токен проверяется на каждом защищённом запросе, роль берётся
только из ответа сервиса учётных записей, неполная сессия не проходит.

Приёмка:

- без заголовка, с неверной схемой, с двумя заголовками, со слишком длинным токеном
  возвращается `401` в едином формате;
- неактивная сессия и сессия без пройденных факторов дают `401`;
- недоступность сервиса учётных записей даёт `503`, а не `401` и не `500`;
- пользователь на административном маршруте получает `403`, отказ попадает в журнал;
- данные пользователя доступны хендлеру через контекст;
- токен не попадает в лог;
- список ролей доступен без токена.

**COORD-6. Прокси.** Регистрация, вход, восстановление пароля, выход и управление
пользователями проходят через сервис.

Приёмка:

- все девять путей доходят до сервиса учётных записей с обрезанным префиксом;
- подделанный клиентом заголовок с адресом не пробрасывается, адрес формируется заново;
- заголовки с идентификатором и ролью пользователя от клиента не доходят;
- недоступность сервиса даёт `503` в JSON, а не `502` текстом;
- выход без токена — `401`, список пользователей с ролью пользователя — `403`;
- тела запросов и ответов не попадают в лог.

Итог этапа: сервис поднимается в compose, вход и регистрация работают через него,
авторизация проверяется, база и клиент Крипто-модуля готовы к следующему этапу.

### Этап 2. Сообщения

| Тикет | Исполнитель | Оценка, дней |
|---|---|---|
| COORD-8. Методы шифрования | Dev A | 0.5 |
| COORD-11. Журнал операций | Dev A | 0.5 |
| COORD-12. Чтение сообщений | Dev A | 1.5 |
| COORD-9. Ключи RSA | Dev B | 1.5 |
| COORD-10. Шифрование | Dev B | 2 |
| COORD-13. Расшифрование | Dev B | 1 |

COORD-8, COORD-11 и COORD-12 ждут COORD-4. COORD-10 ждёт COORD-8 и COORD-9.
COORD-13 не зависит от COORD-10 и может вестись параллельно.

**COORD-8. Методы.** Список методов публичный, переключение доступно администратору,
признак включённости используется при шифровании.

Приёмка:

- список отдаётся в стабильном порядке и без токена;
- запрос на переключение без поля `enabled` возвращает `400` и не меняет состояние;
- неизвестный код метода — `404`, неверный тип содержимого — `415`;
- пользователь получает `403`, запрос без токена — `401`;
- переключение попадает в журнал с кодом метода;
- хелпер проверки метода возвращает «выключен» для неизвестного кода, а не ошибку.

**COORD-11. Журнал.** Операции пишутся, ответ пользователю от журнала не зависит.

Приёмка:

- все шесть типов операций пишутся с осмысленной ссылкой;
- анонимный субъект даёт `NULL`;
- отмена исходного запроса не мешает записи;
- ошибка записи не меняет код ответа и не приводит к панике;
- в записях нет текстов сообщений, ключей и токенов, проверяется тестом по подстрокам.

**COORD-12. Чтение сообщений.** Список и карточка работают с учётом роли, ключи видит
только владелец.

Приёмка:

- пользователь видит только свои сообщения, ключи заполнены;
- администратор видит все, но по чужим сообщениям ключей нет;
- чужое сообщение для пользователя — `404`, а не `403`;
- границы пагинации проверяются, пустой результат отдаётся пустым массивом;
- ошибка распечатывания ключа даёт `500`, а не `400`;
- сообщение с ещё не готовым ключом отдаётся без ключей и со статусом `200`.

**COORD-9. Ключи RSA.** Пара генерируется один раз на пользователя, закрытая часть
хранится только запечатанной, системный ключ подписи создаётся при старте.

Приёмка:

- десять параллельных вызовов дают ровно одну генерацию, проверяется под `-race`;
- готовый и генерирующийся ключ не запускают повторную генерацию;
- ошибка генерации или запечатывания переводит ключ в состояние сбоя, повторный вызов
  пробует снова;
- распечатывание сохранённого ключа возвращает исходный PEM;
- системный ключ создаётся при старте и не блокирует healthcheck;
- PEM и мастер-ключ не попадают в лог.

**COORD-10. Шифрование.** Оба метода шифруют, сохраняют сообщение и возвращают ключи
владельцу вместе с метриками.

Приёмка:

- Кузнечик: `201`, ключ и IV в ответе, время шифрования больше нуля, время генерации
  ключа равно нулю;
- RSA с готовым ключом: `201`, время генерации берётся из записи ключа;
- RSA с генерирующимся ключом: `409` с кодом `key_generating`;
- выключенный метод: `409` с кодом `method_disabled`;
- пустой текст, текст больше 64 КиБ, неизвестный метод — `400`;
- недоступность Крипто-модуля — `503`;
- операция попадает в журнал с идентификатором сообщения;
- текст сообщения и ключи не попадают в лог.

**COORD-13. Расшифрование.** Расшифровка идёт по данным из запроса, время фиксируется
только для своего сообщения.

Приёмка:

- цикл шифрования и расшифрования возвращает исходный текст для обоих методов;
- неверный ключ даёт `400` с кодом `bad_key`, а не `500`;
- битый шестнадцатеричный шифртекст — `400` с кодом `bad_ciphertext`;
- неверная длина ключа или IV — `400` с кодом `bad_key`;
- для своего сообщения обновляется время расшифрования, для чужого — нет, и в журнал
  пишется отказ;
- выключенный метод не мешает расшифровать ранее созданное сообщение.

Итог этапа: сообщение можно зашифровать, увидеть в списке, открыть и расшифровать;
администратор видит чужие сообщения без ключей.

### Этап 3. PDF и подпись

| Тикет | Исполнитель | Оценка, дней |
|---|---|---|
| COORD-14. PDF с подписью | Dev B | 2 |
| COORD-15. Проверка подписи | Dev A | 1.5 |

COORD-15 не начинается, пока не смержен COORD-14: без реального файла проверять нечего.
Если Крипто-модуль к этому моменту не подтвердил операции над готовым хешем, этап
сдвигается, а не выполняется по предположению.

**COORD-14. PDF.** Документ формируется из сохранённых данных, подписывается системным
ключом, доступен только владельцу.

Приёмка:

- файл открывается в просмотрщике, русский текст читается без искажений;
- дата внутри документа совпадает с датой создания сообщения, а не с текущей;
- файл начинается с заголовка PDF и заканчивается блоком подписи;
- разбор блока даёт логин подписанта и время, хеш файла совпадает;
- администратор на чужом сообщении получает `404`, отказ попадает в журнал;
- при недоступном системном ключе — `503`;
- заголовки ответа корректны, размер известен заранее;
- два вызова подряд дают разные подписи, обе проверяются.

**COORD-15. Проверка подписи.** Публичный приём файла, проверка целостности
и подлинности, понятный ответ для повреждённого документа.

Приёмка:

- подписанный файл даёт `valid: true` с логином и временем;
- изменение любого байта в теле документа даёт `valid: false`;
- изменение логина или времени в метаданных тоже даёт `valid: false`;
- файл без блока, обрезанный блок, битая кодировка, неверная длина подписи дают
  `valid: false` со статусом `200`;
- файл больше 10 МиБ — `413`, не PDF — `400`, не multipart — `415`;
- недоступность Крипто-модуля — `503`;
- в ответе при `valid: false` нет поля с датой;
- запись в журнал содержит `NULL` в поле пользователя.

Итог этапа: полный цикл от сообщения до проверки подписи работает на стенде.

### Этап 4. Сквозная проверка

**COORD-16**, совместно. Стенд из четырёх сервисов, сценарий целиком, негативные проверки,
отдельная задача в пайплайне.

Приёмка:

- сценарий проходит от регистрации до проверки подписи без ручных действий;
- негативные проверки дают ожидаемые коды: `401`, `403`, `404`, `409`, `400`;
- сценарий запускается отдельной задачей и не тормозит обычные проверки;
- при падении сохраняются логи контейнеров;
- на стенде используется короткий ключ RSA, в рабочей конфигурации остаётся длинный.

Ограничение по длине ключа на стенде связано с тем, что генерация длинного ключа
занимает десятки минут. Это ограничение стенда, а не изменение требований.

## 5. Общие критерии приёмки

Действуют для любой задачи независимо от этапа. Задача не принимается, если не выполнен
хотя бы один пункт.

По коду:

- `gofmt -l .` не выводит ничего;
- `go vet ./...` без замечаний;
- `golangci-lint run` без замечаний;
- `go test -race -cover ./...` зелёный;
- покрытие затронутых пакетов не ниже 80 процентов;
- в диффе нет `TODO`, отладочных выводов, закомментированного кода и заглушек,
  возвращающих фиктивные данные.

По поведению:

- новое поведение покрыто тестами, включая ошибочные ветки;
- коды ошибок и структура тела соответствуют `contracts.md`;
- ни в ответах, ни в логах нет секретов, токенов, ключей и текстов сообщений.

По процессу:

- ветка ответвлена от актуального `COORD-develop`;
- сообщение коммита соответствует `COORD-<номер>. <описание>`;
- PR содержит ссылку на тикет, описание изменений и отметку об изменении контракта;
- тесты зелёные, есть одно одобрение;
- README обновлён, если появились новые переменные окружения или маршруты.

Изменения контракта. Если меняется сигнатура интерфейса, имя поля в DTO, формат хранения
или код ошибки, это оформляется отдельным PR в `contracts.md` и `internal/ports`
до начала работы, а не попутно. Иначе вторая половина команды узнает об изменении
уже после мержа.

## 6. Контрольные точки

Промежуточные демонстрации, чтобы не обнаружить расхождение в конце. Проводятся
по завершении этапа, без привязки к календарю.

| Этап | Что показываем |
|---|---|
| 0 | контракты, пакеты `sealed` и `pdfsig`, тесты |
| 1 | сервис в compose, вход и регистрация через него, `/api/me`, `/api/roles`, `/api/methods` |
| 2 | шифрование и расшифрование обоих методов, список и карточка сообщений, журнал |
| 3 | PDF с подписью и проверка подписи |
| 4 | сквозной сценарий в пайплайне, тестовый стенд |

Демонстрация — не отчёт, а прогон сценария на стенде. Если что-то не показывается,
задача не готова, даже если PR смержен.

## 7. Риски

**Долгая генерация ключа RSA.** Генерация длинного ключа занимает десятки минут, и первый
запрос на шифрование вернёт `409`. Это ожидаемое поведение, но интерфейс должен быть
к нему готов. Если ожидание неприемлемо, обсуждается снижение размера ключа; это решение
не уровня разработчика.

**Крипто-модуль не предоставляет операции над готовым хешем.** Тогда формат контейнера
подписи придётся менять, а вместе с ним COORD-14 и COORD-15. Проверяется на этапе 0,
до проектирования PDF.

**Сервис учётных записей отвечает не так, как ожидаем.** Контракт проверки токена
и поведение выхода фиксируются до COORD-7. Если ответы отличаются, меняется только клиент,
middleware не трогаем.

**Незакрытые согласования с интерфейсом.** Формат шифртекста, состав полей ролей,
отображение ключей в списке. Это не блокирует бэкенд полностью, но блокирует приёмку
этапа 2.

**Расхождение зон ответственности.** Самый частый источник конфликтов — общие файлы.
Разделение по файлам зафиксировано в `contracts.md`; отступать от него можно только
через PR с изменением контракта.

**Отсутствие соглашений в ветке разработки.** Если `styleguide.md` не влит вместе
с контрактами, ревью становится субъективным, а замечания — противоречивыми.

## 8. Условия завершения работ

Сервис готов к передаче, когда:

- все тикеты `COORD-3`…`COORD-17` закрыты;
- пайплайн `COORD-develop` зелёный, образ `smp-coord:test` собран и развёрнут
  на тестовом стенде;
- сквозной сценарий проходит на стенде без ручных шагов;
- `contracts.md` соответствует фактическому коду;
- README позволяет поднять сервис с нуля по инструкции, без обращения к автору;
- известные ограничения записаны: собственный контейнер подписи вместо PAdES,
  длительная генерация ключа, отсутствие ротации мастер-ключа.
